## 任务 1：技能递归复制的完整 TOCTOU 防护

**交付物：** `importSkill` 在校验后源目录被替换、深层条目类型变化或复制中断时都拒绝导入，并且不会留下最终半成品。

### 步骤 1：编写失败测试

在 `src/main/skillDiscovery.test.ts` 增加测试辅助端口或受控 hook，使以下替换点可确定复现：

```ts
it("拒绝深层目录在校验后变为根外 symlink", async () => {
  const source = await createSkillTree();
  const nested = path.join(source, "nested");
  const outside = await fs.mkdtemp(path.join(os.tmpdir(), "ic-skill-outside-"));
  await fs.writeFile(path.join(outside, "secret.txt"), "secret", "utf8");

  const fsPort = createFsPortWithHook({
    beforeRecursiveEntry: async (from) => {
      if (from === nested) {
        await fs.rm(nested, { recursive: true, force: true });
        await fs.symlink(outside, nested, "junction");
      }
    },
  });

  await expect(importSkill(discovered(source), targetRoot, home, fsPort))
    .rejects.toThrow("skill source outside known roots");
  await expect(fs.stat(path.join(targetRoot, "review"))).rejects.toThrow();
});
```

同时加入：

- 文件在 `lstat` 后变为 symlink 或目录时拒绝。
- 目录自环和文件 symlink 不会被复制。
- `copyFile` 抛错时临时目录被删除，最终目标不存在。
- 目标名称竞争时不覆盖已有目录。
- Windows 风格分隔符、点前缀和驱动器前缀仍被拒绝。

若不希望公开 `fsPort`，将 hook 限定为模块内部测试注入，并在测试中只暴露最小 `lstat/realpath/readdir/copyFile/mkdir/rm/rename` 端口。

### 步骤 2：运行测试确认失败

运行：

```cmd
npx vitest run src/main/skillDiscovery.test.ts
```

预期：新增的深层替换和失败清理用例失败，现有入口级安全用例保持通过；失败原因应显示当前 `copyDir` 只在递归条目处 `lstat`，没有 canonical containment 和原子发布。

### 步骤 3：实现最小安全复制

在 `src/main/skillDiscovery.ts` 中：

1. 把 `validateSourceDir` 返回值扩展为包含 canonical source 和已知 canonical roots 的复制上下文，避免递归时重新计算不可信根。
2. 将 `copyDir(source, target)` 改为接收复制上下文和可注入文件系统端口。
3. 每次进入目录、递归目录和复制文件前重新执行 `lstat`；目录实体再执行 `realpath` 并确认 `isInsideRoot`。
4. 用 `visited` 保存 canonical directory identity，遇到重复身份直接跳过，防止链接/目录环。
5. 目标写入前先创建唯一临时目录；复制完成后校验目标类型，再用 `rename` 原子提交到最终名称。
6. 所有异常路径 `finally` 清理临时目录；最终目录只在 rename 成功后可见。
7. 重新检查名称竞争：最终 rename 遇到已存在目标时尝试下一个 `-imported` 名称，而不是覆盖。

不要跟随任何 symlink；不要通过 `fs.stat` 把链接解析成普通目录；错误信息继续使用现有中性语义。

  await expect(ctx.hmr.restart("plugin")).rejects.toThrow("restart failed");

it("合并连续文件事件并串行执行 restart", async () => {
  const events = createFakeWatchEvents();
  const calls: string[] = [];
  let release!: () => void;
  const running = new Promise<void>((resolve) => { release = resolve; });
  const watcher = createHostHmrWatcher({ watch: events.watch });

  const off = await watcher.watchPath("example", "fixture/client.js", async () => {
    calls.push("start");
    await running;
    calls.push("end");
  });

  events.emit("change", "fixture/client.js");
  events.emit("change", "fixture/client.js");
  await waitFor(() => calls).toEqual(["start"]);
  release();
  await waitFor(() => calls).toEqual(["start", "end"]);
  expect(calls).toEqual(["start", "end"]);
  await off();

### 步骤 3：实现 host watcher adapter

创建 `src/main/pluginBoot/hmrWatcher.ts`：

```ts
export interface HostHmrWatcherOptions {
  debounceMs?: number;
  fsWatch?: typeof fs.watch;
  log?: (level: "warn" | "error", message: string, data?: unknown) => void;
}

export interface HostHmrWatcher {
  watchPath(id: string, fileOrDirectory: string, restart: () => Promise<void>): Promise<() => Promise<void>>;
  dispose(): Promise<void>;
}
```

实现要点：

- 使用 `fs.watch`，不把 watcher 依赖放进 `vendor/kernel-hmr`。
- 每个 `id` 只允许一个 active registration；重复注册先异步 dispose 旧监听。
- 事件通过 `setTimeout` 去抖；同一 id 维护 `running` 和 `pending` 状态，保证 restart 串行。
- restart 失败只记录错误，不删除 registration；pending 事件可继续触发下一次尝试。
- `watchPath` 返回幂等 disposer；全局 `dispose` 清理所有 timers、FSWatcher 和 registrations。
- 监听启动或路径校验失败时，关闭已打开资源后抛出带 `cause` 的错误。

### 步骤 4：接入 plugin boot 的开发模式

在 `src/main/pluginBoot/compose.ts`：

- 为 `PluginBootOptions` 增加可选 host HMR watcher factory，默认仅在非 production 且显式启用时创建。
- 暴露 `watchPlugin(id, path, restart)` 或等价 typed port；内部将 host watcher disposer 挂到 boot dispose 流程。
- 不让 HMR watcher 直接改 loader tree；restart callback 由调用方提供，失败由 watcher 记录。
- `createPluginBoot` 的 `dispose()` 先停止 host watcher，再卸载 root fiber。

- 用 staging fixture 文件注册 watcher。
- 写入变更，断言 callback 只调用一次。
- dispose boot 后再次写入，断言 callback 不再调用。

### 步骤 3：实现 out preflight

创建 `scripts/packaging/outPreflight.ts`，提供：

```ts
export interface OutPreflightResult {
  outputRoot: string;
  removed: string[];
  lockDiagnostics: string[];
}

export async function cleanPackageOutput(
  outputRoot: string,
  repositoryRoot: string,
): Promise<OutPreflightResult>;
```

实现约束：

- `path.resolve(outputRoot)` 必须等于仓库根下的 `out` 或其已知 package 子目录。
- 只删除本项目生成的 package 目录和 Forge 临时产物，不删除整个仓库或用户目录。
- 删除失败时进行有限次数、递增间隔重试；最终返回文件路径、错误码和建议，不循环重试。
- Windows 下不自动杀死未知进程；若可安全识别为当前 package 测试子进程，只记录其 PID/镜像路径供调用方处理。
- 成功清理后再由 Forge package 生成新产物。

## 依赖与执行顺序

1. 任务 1 先完成技能安全边界；它独立于其他任务，可立即审查。
2. 任务 2 依赖现有 kernel HMR API，但不依赖 UI；完成后再接 host boot。
3. 任务 3 依赖已有插件 client/slot/protocol，并应在任务 2 后执行以避免同时调试宿主生命周期。
4. 任务 4 可与任务 3 并行审查，但实际迁移应在真实 acceptance fixture 稳定后进行，避免把测试 helper 错误带入宿主测试。
5. 任务 5 必须在源实现和测试稳定后执行；package 只验证新产物。
6. 任务 6 是最终门禁，不得在全量验证前声明阶段完成。

## 规格覆盖自检

- 规格第 4 节技能安全：任务 1 覆盖入口、递归、失败清理、原子提交和竞态测试。
- 规格第 5 节 HMR：任务 2 覆盖 kernel 注册、真实 `fs.watch`、去抖、串行 restart、失败保留和 dispose。
- 规格第 6 节真实 UI：任务 3 覆盖 fixture client、双根协议、preload、renderer、panel/settings 呈现和停用撤销。
- 规格第 7 节静态 spine：任务 4 覆盖 helper、生产 guard、child suite 继承和 source 搜索约束。
- 规格第 8 节 Forge/out：任务 5 覆盖安全路径、锁诊断、native 裁剪、package 和 packaged smoke。
- 规格第 10/12 节验收矩阵与完成定义：任务 6 运行定向、全量、类型、package 和工作树安全验证。
